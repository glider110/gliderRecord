§ PyTorch、ONNX 与 TensorRT 部署链路

深度学习模型在工程上通常要经历“训练框架 -> 中间格式 -> 硬件优化运行时”三段式落地，而不是直接把训练代码搬到设备上运行。

§ 三者分工

组件 角色 产物 关注点
PyTorch 训练框架、模型定义 .pt / .pth 灵活性、开发效率
ONNX 中间表示格式 .onnx 互操作性、标准化
TensorRT 推理优化器与运行时 .engine / .plan 低延迟、高吞吐

§ 标准流程

flowchart LR
    A[PyTorch 训练模型] --> B[导出 ONNX]
    B --> C[TensorRT 编译优化]
    C --> D[NVIDIA GPU 部署运行]

§ 为什么要有 ONNX

ONNX 的价值不是“跑得更快”，而是把模型从训练框架里解耦出来：

  • 让 PyTorch 训练产物能进入统一部署链路
  • 降低训练环境与部署环境之间的耦合
  • 为 TensorRT、RKNN、NCNN 等后续优化器提供稳定输入

§ 为什么 TensorRT 适合 Jetson

TensorRT 的核心价值是针对 NVIDIA GPU 做激进优化：

  • 层融合，减少 kernel 启动和内存访问
  • FP16 / INT8 量化，提高速度和能效
  • 自动为当前硬件挑选更优 kernel

这意味着在 Jetson AGX Orin 这类平台上，TensorRT 往往比直接跑原始框架推理更适合量产部署。

§ 与 RKNN / NCNN 的关系

  • TensorRT：绑定 NVIDIA GPU
  • RKNN：绑定 Rockchip NPU
  • NCNN：更偏通用、轻量、跨平台 CPU/Vulkan 推理

因此模型部署路线通常由目标硬件决定：

  • Jetson：PyTorch -> ONNX -> TensorRT
  • RK3588：PyTorch -> ONNX -> RKNN
  • 通用移动端 / CPU：PyTorch -> ONNX / 自定义转换 -> NCNN

§ 工程判断

如果项目目标是机器人或 AMR 的高性能边缘推理，真正要对比的往往不是“模型能不能跑”，而是：

  1. 部署后时延是否满足控制周期
  2. INT8 / FP16 量化后精度退化是否可接受
  3. 工具链是否与目标平台绑定过深

这些问题比单纯比较 TOPS 更接近真实工程决策。
